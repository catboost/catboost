# Remaining CUDA-to-Metal work

Reviewed 2026-09-12 against the local CUDA sources at upstream revision `e68a1c021f` and the current experimental Metal backend. This is a source review; no new training runs or implementation changes were made.

The existing port runs numeric RMSE training on the M3: Plain/DocParallel boosting, symmetric trees, unit weights, L2/Cosine scores, and one Newton leaf update. It exports ordinary CatBoost models. The earlier 66-test result checks the translated arithmetic and model interoperability; it is not a comparison against execution on NVIDIA hardware.

The largest remaining jobs are the optimized partition/histogram pipeline, general weighted objectives, and native CatBoost integration. Categorical features, Ordered boosting, and ranking add substantial independent subsystems.

For native dispatch, the recommended design is `task_type="GPU"` selecting Metal on Apple silicon, with explicit Metal backend metadata and capability checks. This is a proposal. Adding a third `METAL` enum would require auditing the existing two-task option masks, defaults, validation, and quantization assumptions throughout CatBoost. The current standalone estimator still uses its own `METAL` parameter.

The Darwin build must enable Objective-C++, preserve static trainer registration, and link Metal/Foundation/Objective-C runtime dependencies consistently with CatBoost's vendored C++ runtime. The prototype's independent system-Clang command is insufficient for this integration.

## M3-specific adaptations

Current histograms and leaf statistics use global compare-and-swap float additions for individual observations. M3 belongs to Apple's Apple9 GPU family and supports native floating-point atomics. Evaluate native `atomic_float` together with threadgroup-local histograms and staged reductions. CUDA shared-memory layouts and launch sizes need retuning: Apple's table lists 32 KiB threadgroup memory for Apple9, while some CUDA histogram variants use larger arrays. Query actual device/pipeline limits. [Apple feature tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf)

Current buffers already use shared memory and are reused during a fit; pipelines are cached. Remaining costs include synchronization, repeated-fit allocation/copies, and histogram contention. Apple recommends reducing atomic contention and profiling resource usage; no speedup is established by this review. [Apple Metal compute guidance](https://developer.apple.com/videos/play/tech-talks/10580/)

Histogram memory currently scales as `8 * 2^depth * feature_count * maximum_bin_count` bytes: at depth 8 and 256 bins, **0.5 MiB per feature** before other buffers. Compact offsets and feature tiling should precede raising the 1 GiB workspace, 512 MiB output, depth-8, and 2^24-row limits. These are implementation limits. Four-byte feature packing improves load reuse; it does not reduce storage relative to four existing byte columns.

Precision needs attention alongside performance. CUDA uses float histograms but double intermediates in partition reductions, Cosine scores, and host leaf calculations. Current Metal uses float throughout those calculations. Test cancellation, large partitions, and near-tied scores; consider staged/compensated reductions or small host-double final calculations. Parent-minus-child histogram reuse increases the need for this validation. See [score_calcers.cuh](/Users/jefferypowell/Desktop/Catbooster/catboost/cuda/methods/kernel/score_calcers.cuh) and [update_part_props.cu](/Users/jefferypowell/Desktop/Catbooster/catboost/cuda/cuda_util/kernel/update_part_props.cu:119).

## Delegation and acceptance

Agree on shared dataset/partition/statistic layouts and an iteration-state interface first. Then delegate:

1. **Partition agent:** reorder/gather, offsets, segmented reductions, precision cases.
2. **Histogram agent:** compact layout, local accumulation, parallel scans; join partition work for smaller-child reuse.
3. **Objective agent:** sample weights, Logloss/CrossEntropy, iterative leaf estimates, sampling.
4. **Integration agent:** native trainer, Pool/model adapters, iteration lifecycle, Darwin packaging. Packaging can be split out once the target/interface is fixed.
5. **Split-reduction agent:** GPU winner reduction and tie semantics; independent of partitioning.

For each completed port, compare intermediate statistics, selected splits, leaves, and model outputs against CUDA-derived fixtures. Existing scalar reference tests remain useful; NVIDIA-produced fixtures or runs are needed before claiming measured CUDA agreement. Add weighted, missing-value, imbalanced, large-partition, and near-tie cases as applicable. Measure representative M3 workloads when the corresponding implementation changes.

Single-M3 training does not need multi-GPU collectives, peer-device transfers, MPI workers, or a literal clone of the CUDA memory manager. Standard quantization, model saving, CPU inference, label handling, and training-control utilities should be reused. Snapshot recovery belongs in CUDA feature parity; `init_model` continuation and Python iteration callbacks are separate extensions because the current CUDA trainer does not support them. See [train.cpp](/Users/jefferypowell/Desktop/Catbooster/catboost/cuda/train_lib/train.cpp:305).
